# Конвейер качества в харнессе — дизайн

Дата: 2026-11-16. Статус: одобрен пользователем 2026-11-16 (план ниже). Раздел «Приложение» — детали
компонентов из первой версии дизайна; где они расходятся с планом, прав план.

## План: процесс Tan как основа харнесса + конвейер качества + исполнители и панель управления

### Context

Пользователь хочет надёжный, качественный и гибкий конвейер кода по образцу Lauren Tan (11 000 PR в месяц,
около 0,5% откатов). Он решил перестроить наш процесс под её подход, а не наоборот. Всё должно стать частью
харнесса и работать по умолчанию во всех сессиях и новых проектах.

Подход Tan в сути:
- поправки превращаются в детерминированные проверки, а не в прозу;
- кодовая база — «сад», который агенты копируют;
- проверка идёт через реальный запуск с доказательствами (карта фич, verify-скиллы);
- находки ревью подтверждаются запуском;
- плейбуки по типам задач и именованные принципы;
- внешний цикл автоматизируется только после того, как внутренний чист.

Всё это есть в её библиотеке pstack (MIT, `github.com/backnotprop/pstack` — зеркало `cursor/plugins/pstack`).
У pstack есть механизм адаптеров под харнессы.

Почему сейчас. Данные из 135 поправок пользователя:
- неверно понятые требования (~30);
- непонятный интерфейс (~29);
- потерянные указания (~20);
- «готово» без проверки (~18).

Из ~150 правил харнесса кодом обеспечены 13. В rpg нет прогона реального интерфейса. Gemini через Antigravity
сейчас сломан: режим `plan`, все разрешения запрещены, даже «ответь OK» падает с `permission_required`.

Предыдущий дизайн: `~/dev/gpt-harness/docs/superpowers/specs/2026-11-16-conveyor-design.md` (C0–C10). Первым
шагом реализации он переписывается под этот план. Главное изменение: процесс — pstack, а не свои скиллы.

### Решения пользователя (2026-11-16)

- **Процесс.** pstack — основной процесс по умолчанию (`poteto-mode`). superpowers и GSD остаются
  установленными, но их автозапуск и «обязательно используй скиллы» на старте сессии отключаются; вызываются
  только явно.
- **Исполнители.** Сложное: Sol 6.1 → Sonnet. Простое: Gemini (полноценный, правит код) → Luna → Haiku.
  Opus только оркеструет и делает дизайн.
- **Порог Codex → Claude.** Автопереключение на 80% лимита Codex (Sol → Sonnet, Luna → Haiku); значение
  меняется в панели.
- **Журнал приёмки, все четыре защиты:**
  1. детерминированная привязка каждой побудительной фразы пользователя к пункту журнала;
  2. пересказ требований в начале нетривиальной задачи;
  3. обязательный чек-лист в итоговом сообщении;
  4. смысловая сверка Gemini один раз при «готово».
- **Панель.** Настраивается, какая модель и с каким уровнем effort для каких задач. Новые модели добавляются быстро (каталоги
  провайдеров), плюс порог и цепочки. Тексты `CLAUDE.md` в панели не редактируются.
- **Обновление CLI из панели.** Codex и Gemini:
  - Linux (bro): официальный `agy` с закреплённым SHA256, без патча; окружение без маркеров SSH; вход через
    Secret Service.
  - Windows: рецепт пользователя `ineligible → inexigible` применяется только при точном совпадении
    известного исходного SHA256 и с проверкой ожидаемого результата (GUI 2.32.1: 14 замен; CLI 1.5.9:
    15 замен). Неизвестная сборка не патчится, а помечается «нужно исследовать». Бэкап оригинала, откат,
    manifest, проверка реальным запросом — всё по процедуре пользователя.

### Архитектура: три слоя

1. **Процесс — pstack Tan** (как есть, закреплённая версия): плейбуки, 24 принципа, `correct`, `interrogate`,
   `create/maintain-verification-skill`, `arena`, `swarm`, `blast-radius`, `in-your-own-words`,
   `show-me-your-work`. Подключается через **наш адаптер харнесса**: каждое «запусти агента с ролью X»
   превращается в «запусти исполнителя уровня X» через диспетчер.
2. **Обеспечение — конвейерные гейты.** Принципы Tan становятся обязательными через хуки и обёртки:
   - «Prove it works» — Stop-гейт с доказательствами;
   - «Encode lessons as lints» — `correct` и очередь проверок петли;
   - «Sequence work into verifiable units» — гейт исполнителя.
3. **Исполнители и управление:** диспетчер уровней, провайдеры с цепочками и порогами, `gem.sh`, панель.

Наша уникальная инфраструктура сохраняется и обслуживает процесс: `luna.sh` и демон, RAM/heavy-гейты,
pytest-бюджет, уборка, петля обучения, worktree-скрипты.

### Фазы

Каждая фаза — отдельный срез. Реализация — исполнитель уровня complex, разведка — simple, затем критики
(в pstack-фазах — `interrogate`), раунд исправлений, коммит в ветку `gpt-harness`; payload Linux + Windows +
манифест — в той же фазе. Общие обёртки правятся через `.next` и `luna-swap-when-idle.sh`, никогда на месте.

**F0. Основа процесса (pstack + адаптер + чистка прозы)**
- Вендорить pstack в payload с закреплённым коммитом, `LICENSE` и `SYNC-LOG`. Ставится инсталлятором в
  `~/.claude/skills/` (без маркетплейса и автообновлений).
- Адаптер `docs/harness/bro-harness.md` по образцу pstack `docs/harness/claude-code.md`. Сопоставление:
  `Task` → диспетчер `~/.claude/scripts/conveyor/exec.mjs --tier <tier> --brief <file>`; `readonly` → `-r`;
  `environment: cloud` → worktree через `wt-new.mjs`; модели по ролям → уровни.
- Файл ролей `~/.claude/rules/pstack-models.md` генерируется из `orchestration.json`: роли pstack (feature,
  bug-fix, hardest, judgment, reviewers, arena runners, swarm workers…) → уровни/провайдеры.
- `poteto-mode` — вход по умолчанию. SessionStart-хук заменяет текущий автозагрузчик `luna`; superpowers
  `using-superpowers` и GSD-хуки, навязывающие процесс, отключаются в `settings.json`, плагины остаются.
- Переписать `CLAUDE.md` и скилл `luna`:
  - процессную прозу, которую покрывают плейбуки pstack (брифы, критики, порядок работы), удалить;
  - остаются инфраструктурные правила (ресурсы, уборка, исполнители, дизайн за Opus);
  - `luna-critics` становится конфигурацией ревьюеров для `interrogate` (разнообразие провайдеров
    вместо персон) плюс персона «Рядовой пользователь» для интерфейсов.
- C9 гигиена:
  - расхождения прозы и кода (слоты heavy-gate: 2 против 3; порог RAM pytest);
  - блоки на голый `pytest` и правку обёрток на месте;
  - предупреждение на голый `git worktree add`.
- Закрыть NU-20261111-1 петли (порог 60%) — заменён настраиваемым порогом 80%.

**F1. Исполнители**
- `~/.claude/conveyor/orchestration.json` — единственный источник правды:
  - уровни (complex, simple, review, scout) → упорядоченные провайдеры с моделью и effort;
  - каталог моделей, включая новые;
  - порог Codex 80% (отдельно 5-часовое и недельное окна, гистерезис);
  - режимы гейтов, роли pstack.
- Диспетчер `exec.mjs`: выбирает провайдера по цепочке и состоянию из `providers.json`:
  - квота Codex из `luna-overview.mjs` `codexLimits`;
  - Gemini: 429/RESOURCE_EXHAUSTED/«exhausted capacity»;
  - Claude: `$.session.usage()` через панель/heartbeat.

  Вызывает `luna.sh`, `gem.sh` или печатает инструкцию для сабагента Claude (Sonnet/Haiku через Agent с тем
  же брифом). Пишет одну строку о переходе.
- `gem.sh`: контракт как у `luna.sh` (бриф, `-r/-w`, `-C`, разделы результата, `.status`, `luna-watch`,
  `luna-stop`, `registry.mjs`). Запуск:
  `run-agy -p --model <из конфига> --mode auto|plan --sandbox --effort … --output-format stream-json` в
  каталоге проекта. Общий код статусов и RAM-гейта выносится в lib, а не копируется.
- Починка MCP `antigravity-parallel` для текстовых пакетов (`/srv/docker/compose/antigravity-parallel/src/
  parallel_acp.py`: режим и обработчик `session/request_permission`).

**F2. Панель Luna** (`~/.claude/local-plugins/luna-panel/hooks/register.tsx`; данные —
`~/.claude/scripts/luna-overview.mjs`; работа через скилл `plugin-authoring`; вёрстка — Opus сам)

Дизайн и удобство — отдельный первоклассный результат (пользователь, 2026-11-16: «плотность, читаемость,
насыщенность инфой… всё должно быть на высоте, особенно удобство»). Делает Opus сам, не делегируя.
- **Сначала разбор.** Скриншоты текущей панели, все места, где приходится искать, читать мелкое или делать
  лишние клики; что пользователь смотрит чаще всего (лимиты, зависшие задачи, активная цепочка) и что
  меняет чаще всего (модель и effort для задачи, порог).
- **Информационная архитектура по частоте использования.** Сверху одна строка-сводка «всё ли в порядке»:
  лимиты трёх провайдеров с цветом, активная цепочка, внимание на зависания. Ниже — задачи. Настройки и
  обновления в отдельной вкладке, но смена модели/effort для уровня и порог доступны в 1–2 действия с главного
  экрана.
- **Плотность и читаемость.**
  - Компактная табличная раскладка без пустот, выровненные числа, единые единицы.
  - Цвет только для состояний (норма, внимание, проблема), иерархия через вес и размер, а не рамки.
  - Подписи по-русски и коротко; полный текст во всплывающей подсказке.
- **Удобство.**
  - Встроенное редактирование прямо в строке уровня: модель → effort → готово.
  - Пресеты одним кликом (например «максимум качества», «экономия Codex», «только Claude»), свои пресеты
    сохраняются.
  - Отмена последнего изменения; подтверждение только для обновлений CLI.
  - Понятные состояния загрузки, устаревших данных и ошибки, с конкретным следующим шагом.
- **Проверка удобства.** Скриншоты в светлой и тёмной теме и на узкой ширине. Критики «Дизайнер» и
  «Рядовой пользователь» работают по скриншотам и сценариям: сменить модель для простых задач; понять,
  почему задача ушла на Sonnet; обновить Codex. Итерации до чистого результата.
- Лимиты Claude, Codex и Gemini; активная цепочка по уровням; журнал переключений.
- **Задачи и сессии всех исполнителей в одном списке** (пользователь, 2026-11-16): кроме задач Codex
  (Sol/Luna), показываются:
  - задачи Gemini через `gem.sh`: те же поля, что у Luna — проект, что делает сейчас, сколько молчит,
    модель/effort, состояние; остановка из панели через стоп-скрипт;
  - пакеты и запросы MCP `antigravity-parallel`: активные элементы, адаптивный лимит;
  - сабагенты Claude (Sonnet/Haiku), запущенные диспетчером.

  У каждой строки метка провайдера; фильтр по провайдеру и проекту. Источник —
  `luna-overview.mjs`, расширенный чтением статусов `gem.sh` (общий формат `.status` и реестр
  `registry.mjs`) и `antigravity_parallel_status`.
- Редактор «модель для задачи»: уровни/роли → провайдер, модель **и уровень effort** (пользователь, 2026-11-16).
  Для каждой модели предлагаются только поддерживаемые ей уровни: Codex — low…max; Gemini/agy — low…max
  через `--effort` и варианты моделей flash-low/medium/high; Claude — по поддержке модели. Выбранный effort
  передаётся исполнителю диспетчером (`luna.sh -e`, `run-agy --effort`, параметр сабагента). Новая модель добавляется из каталога
  провайдера (`agy models`, список моделей Codex, модели Claude) или вводится вручную с проверкой.
  Ползунок порога Codex. Валидация, журнал изменений. Панель — операторский канал: изменения из неё считаются
  решением пользователя; правка конфига в обход панели помечается.
- Обновление CLI (каждый шаг с подтверждением в панели):
  - **Codex:** `npm i -g @openai/codex@<версия>`, применяется, когда демон Luna простаивает; синхронно с
    ожидаемой версией в `install.mjs`.
  - **agy Linux:** официальная сборка → SHA256 → обновление `agy_sha256` в `config/settings.json` →
    проверочный запрос → откат на сохранённый оригинал при ошибке.
  - **agy Windows:** рецепты патча как данные (версия, исходный/ожидаемый SHA256, число замен), строго по
    процедуре пользователя.

**F3. Гейты конвейера**
- Профиль проекта `.claude/conveyor.json` с автоопределением; `check.mjs` (уровни fast/turn, бюджеты,
  heavy-gate).
- Гейт исполнителя («крутиться до зелёного», ≤ 2 раундов) в трёх точках: `luna.sh`, `gem.sh` и хук
  `SubagentStop` для Sonnet/Haiku.
- Журнал приёмки:
  - хук `UserPromptSubmit` дословно записывает сообщения пользователя и выделяет побудительные фразы
    (ru/en);
  - CLI `conveyor ledger`; пересказ в начале нетривиальной задачи (pstack `in-your-own-words`).
- Stop-гейт блокирует, если есть изменения кода и при этом:
  - нет журнала;
  - есть непривязанные фразы;
  - есть открытые пункты;
  - доказательства отсутствуют или устарели;
  - verify не прогнан для пользовательских путей;
  - красная страховочная `turn`-проверка всего диффа;
  - в итоговом сообщении нет чек-листа.

  При «готово» один раз выполняется смысловая сверка Gemini (сообщения пользователя ↔ журнал ↔ дифф).
- Исключения только по проверенной цитате пользователя (логика `verifyEventProvenance` из
  `~/.claude/scripts/learning/extract.mjs`). Первая неделя — режим `warn` для калибровки.

**F4. Верификация (pstack как есть через адаптер)**
- `create-verification-skill` → `verify-kriminalist` и карта фич (пилот). Доказательства в
  `.conveyor/evidence`; скриншоты desktop + mobile уходят «Рядовому пользователю».
- `maintain-verification-skill` — для поддержки.

**F5. Ревью и превращение поправок в проверки**
- `interrogate`: ревьюеры — разные провайдеры (Sol 6.1, Gemini, Luna); находка засчитывается только с
  прогоном.
- `correct` берёт очередь `~/.claude/learning/checks.jsonl` и классы ошибок проекта, строит проверки
  с доказательством «падает на прошлой ошибке», ведёт таблицу правил в `AGENTS.md` проекта.
- Петля обучения остаётся автоматическим сборщиком событий. Её выход питает `correct`, а pstack `reflect` /
  `automate-me` используются вручную.

**F6. Метрики и раскатка**
- Метрики в отчёте петли (`~/.claude/scripts/learning/core.mjs` `buildReport`): поправки на задачу, поправки
  после «готово», раунды гейта, блоки и исключения, проверки от `correct`.
- `verify-*` и профили в rpg и jewel. SessionStart в репо без профиля предлагает
  `create-verification-skill`.

**F7. Гигиена (пользователь, 2026-11-16: все три вида)**
- **H1. Гигиена кода проектов («сад» Tan, еженедельные чистки Buykin).** В профиле проекта
  `.claude/conveyor.json` раздел `hygiene` задаёт счётчики антипаттернов с проверкой на точный текст:
  `eslint-disable`, `setTimeout`, широкий `except Exception`, `type: ignore`, TODO/FIXME, файлы больше N строк,
  мёртвый код. Работает «храповик»: базовая линия хранится в репо, гейт исполнителя блокирует рост любого
  счётчика в диффе, а снижение фиксируется как новая база. Еженедельный прогон предлагает 1–3 маленьких
  среза чистки через `correct` (с вашего согласия). Тренд по проектам идёт в еженедельный отчёт.
- **H2. Гигиена харнесса** (ночной прогон по образцу Orobator). Проверки:
  - проза против кода (например, число слотов heavy-gate, пороги, пути скриптов, упомянутые в `CLAUDE.md`
    и скиллах);
  - синхронность «установлено ↔ payload-linux ↔ payload ↔ manifest» (хэши);
  - мёртвые и дублирующиеся хуки в `settings.json`;
  - устаревшие или противоречивые правила в скиллах.

  Результат — черновики правок и пункты в «needs your decision», ничего не применяется само.
- **H3. Уборка после работы — в код.** Stop-гейт (вместе с F3) проверяет хвосты этой сессии:
  - незавершённые или осиротевшие задачи исполнителей этой сессии (`owner`);
  - временные каталоги и брифы, зарегистрированные сессией;
  - больше одной резервной копии на файл;
  - просроченные worktree этой сессии (`wt-new.mjs` записывает владельца).

  Блок по проверяемым признакам, без эвристик. Исключение — только по словам пользователя.

Не входит сейчас: автономная очередь задач, автослияние PR, формальная верификация — после стабилизации
внутреннего цикла, как советует Tan.

# Приложение: детали компонентов (первая версия)

Дата: 2026-11-16. Статус: черновик на согласование.
Источники: доклад Lauren Tan «All Code Is Slop (Except Mine)» и её библиотека скиллов pstack (MIT),
доклады Andrew Orobator (лестница верификации, гейты), Sonar (двухуровневые проверки в сессии),
Dmitry Buykin (журнал приёмки, агенты молча пропускают работу). Данные о текущем состоянии взяты из аудита
харнесса, 135 поправок пользователя (`~/.claude/learning/events.jsonl`, июль–ноябрь 2026) и обзора проектов
rpg, kriminalist, jewel.

## 1. Зачем

Пользователь хочет надёжный конвейер кода: задача на входе — проверенный качественный результат на выходе,
с минимумом его поправок. Это должно стать частью харнесса и работать по умолчанию во всех сессиях и во всех
проектах, включая новые.

Сейчас качество держится на прозе (≈63 КБ правил в `CLAUDE.md` и скиллах) и на статическом ревью критиков.
Реальные поправки пользователя показывают, где это не работает:

| Класс ошибки | Поправок | Где ловить по пирамиде Tan |
|---|---:|---|
| Неверно поняты требования или правила предметки | ~30 | Канонические правила проекта + приёмочные сценарии |
| Непонятный игроку интерфейс (что выбрано, какая фаза, что делать) | ~29 | Прогон реального интерфейса с доказательствами |
| Потеряны явные указания (формат, объём, порядок, роль) | ~20 | Журнал приёмки + гейт в конце хода |
| «Готово» до того, как всё сделано и проверено | ~18 | Журнал приёмки + доказательства |
| Зависания, мусор, параллельность | ~17 | Хуки харнесса (частично уже есть) |
| Медленные/лишние тесты | ~12 | Бюджеты и уровни проверок |

Принцип Tan: вкладываться снизу вверх — архитектура и линтер → тесты → верификация запуском → проза
только для суждений. Каждая поправка должна превращаться в детерминированную проверку. Автоматизировать
внешний цикл можно только после того, как внутренний перестал производить мусор.

## 2. Цели, не-цели, анти-цели

**Цели**
1. Ни одна задача, менявшая код, не объявляется готовой без доказательств по каждому явному требованию
   пользователя.
2. Код от исполнителя проходит детерминированные проверки проекта до того, как Claude его увидит; при
   падении исполнитель сам дорабатывает («крутится у гейта до зелёного»).
3. В каждом проекте есть способ проверить работу реальным запуском (запуск с пустых данных → прогон как
   пользователь → доказательства → уборка) и карта фич.
4. Повторяющиеся ошибки становятся проверками в коде проекта или харнесса, а не новой прозой.
5. Всё ставится инсталлятором харнесса и работает в новых проектах без ручной настройки (с разумными
   умолчаниями), а проект может уточнить поведение своим профилем.
6. Видно, работает ли это: метрики качества в еженедельном отчёте.

**Не-цели (сейчас)**
- Автономная очередь задач, cron-агенты, автослияние PR. Это следующий этап, после стабилизации внутреннего
  цикла.
- Формальная верификация (TLA+, Lean) и property-based тесты интерфейса (Bombadil) — позже, точечно.
- Переписывание проектов. В проекты добавляются профиль, verify-скилл, карта фич и проверки; рефакторинг
  крупных файлов — отдельные задачи.

**Анти-цели (провал, даже если формально работает)**
- Гейт блокирует обычный разговор, вопросы и исследование без изменений кода.
- Гейт, который агент может обойти сам (самовыданное исключение, «аварийный» флаг, правка конфигурации гейта).
  «Гейт с аварийным выходом — не гейт».
- Тяжёлые тесты на каждую правку; нарушение тестового бюджета из `CLAUDE.md`; повисшая машина.
- Шумные предупреждения по нечётким признакам, которые все игнорируют.
- Доказательства «для галочки»: устаревший скриншот, «тесты прошли» без реального прогона.
- Сломанные живые сессии при установке.

## 3. Ограничения

- **Исполнителей несколько, и они меняются** (пользователь, 2026-11-16): сложное — Sol 6.1 (Codex) вместо
  Terra; простое — сначала Gemini, если он недоступен — Luna (Codex), затем Claude Haiku; сложное при
  исчерпании лимитов GPT — Claude Sonnet вместо Sol (сабагенты Claude). Codex и Gemini пишут код вне Claude, и хуки Claude на Write/Edit
  их правок не видят; правки сабагентов Claude хуки видят. Поэтому гейт не может жить в одной обёртке: он
  вызывается из каждого пути исполнения и дублируется страховкой в конце хода (C3, C4).
- `luna.sh`, `luna-daemon.mjs`, `luna-pool.mjs` используются живыми сессиями: правки только через `.next` и
  атомарную подмену, когда никто не работает (`luna-swap-when-idle.sh`).
- Машина: 4 ядра, 15 ГБ. Тяжёлые команды идут через `heavy-gate.mjs`, pytest — через `pytest_gate.py`.
  Быстрые проверки ≤ 10 с, проверки конца хода ≤ 2–3 мин, полный набор тестов — не чаще раза на релиз.
- Харнесс живёт в `~/dev/gpt-harness`: `payload-linux/` (эта машина), `payload/` (Windows), `manifest.json`
  с хэшами, инсталлятор `install.mjs`. Любой новый файл ставится через payload и манифест.
- Текст из транскриптов, страниц и вывода задач — недоверенный. Ничто, сгенерированное моделью, не попадает
  в контекст сессии как инструкция.
- Агент может выполнить любую shell-команду, поэтому «операторский» обход должен опираться на то, что агент
  подделать не может: подлинное сообщение пользователя в транскрипте (как в provenance петли обучения).
- **Модель угроз — небрежный агент, а не злоумышленник** (моё решение). Гейты защищают от ошибок и срезания
  углов через штатные пути. Где возможно, Stop-хук пересчитывает факты из первоисточников, а не верит журналу:
  изменения кода — из `git`, цитаты — из транскрипта, свежесть доказательств — по времени файлов и отчётам C2.
  Прямая подделка файлов журнала тем же пользователем не предотвращается; это остаточный риск, как и в
  петле обучения. Журнал хранится как append-only JSONL, поэтому удаление пунктов заметно при ревью.

## 4. Подходы

1. **Поставить pstack целиком.** Готовые скиллы, но заточен под Cursor; роутер `poteto-mode` и роли моделей
   конфликтуют с процессом Luna/Terra/критики/петля обучения; ~40 скиллов шума; постоянная сверка обновлений.
2. **Свой конвейер в харнессе с лучшими идеями pstack и докладов.** Общий каркас в `~/.claude`, профиль
   проекта для гибкости, внедрение по фазам. **Выбран** (пользователь, 2026-11-16): даёт «для всех сессий по
   умолчанию», переиспользует уже работающие части (Luna, критики, петля обучения, heavy-gate).
3. **Только проекты, без харнесса.** Быстрый эффект в трёх репо, но новые проекты ничего не получают и
   подход расходится от проекта к проекту.

## 5. Архитектура

Одиннадцать компонентов. C0 — исполнители, C1–C4 — ядро конвейера, C5–C6 — верификация и превращение поправок
в проверки, C7–C9 — качество ревью, метрики, гигиена харнесса, C10 — лимиты и исполнители в панели.

### C0. Исполнители: уровни, провайдеры, запасные варианты

Бриф и гейт не зависят от того, кто исполняет. Claude выбирает **уровень**, харнесс — провайдера:

| Уровень | Основной | Запасной (кончились лимиты) |
|---|---|---|
| `complex` — всё сложнее простого | Sol 6.1 через `luna.sh -m gpt-6.1-sol` | Claude Sonnet (сабагент) |
| `simple` — механика, разведка, критики | Gemini; если недоступен — Luna (`luna.sh`) | Claude Haiku (сабагент) |

- **Gemini — полноценный исполнитель** (пользователь, 2026-11-16: «надо сделать чтоб он был полностью
  функционален»). Сейчас он подключён только как MCP `antigravity-parallel` в конфиге Codex, работает в режиме
  `plan` без инструментов и запрещает любые разрешения; проверка 2026-11-16 показала, что даже запрос
  «ответь OK» падает с `permission_required` (модель пытается вызвать инструмент, ответ пустой).
  Новая обёртка `gem.sh` с тем же контрактом, что `luna.sh` (бриф-файл, `-r`/`-w`, `-C <repo>`, результат с
  разделами `## Changes / ## Verification / ## Deviations / ## Not done`, `.status`, гейт C3, стоп-скрипт,
  наблюдатель зависаний), запускает Antigravity CLI в неинтерактивном режиме в каталоге проекта:
  `run-agy -p --model gemini-3.8-flash-high --mode auto|plan --sandbox --effort … --output-format stream-json`
  (`-w` → `auto` с песочницей терминала, `-r` → `plan`). Исполнитель сам читает файлы, правит код и запускает
  команды; переменная `--add-dir` — только для явно указанных каталогов.
- **MCP `antigravity-parallel` остаётся** для пакетов чисто текстовых подзадач (до 24 параллельно, без файлов):
  классификация, суммаризация, сверка. Его ошибку с `permission_required` на текстовых запросах нужно
  исправить, приёмка: запрос «ответь OK» возвращает `OK`, пакет из 10 текстовых запросов проходит.
- Признак недоступности Gemini — ошибка запуска, `RESOURCE_EXHAUSTED`/429 или «exhausted your capacity»
  (шлюз уже их распознаёт); тогда следующий в цепочке — Luna, затем Haiku.
- Сабагенты Claude получают тот же бриф и тот же контракт результата; гейт для них — хук `SubagentStop`.
- Признак исчерпания лимита — ошибка квоты/usage limit от провайдера (уже распознаётся в `luna.sh`, его
  model-error retry их не повторяет). Переход на запасной — решение Claude по этому сигналу, с одной строкой
  пользователю (как правило «Fallback: never stall» в `CLAUDE.md`).
- `CLAUDE.md` и скилл `luna` переписываются под уровни: Terra заменяется на Sol 6.1, добавляются Gemini и
  запасные варианты.

### C1. Профиль проекта `.claude/conveyor.json` (гибкость)

Необязательный файл в корне репо. Без него действуют автоопределённые умолчания.

```json
{
  "version": 1,
  "fast":  [{"glob": "src/**/*.{ts,tsx}", "run": "npx eslint --max-warnings=0 {files}"},
            {"glob": "**/*.py", "run": "uv run ruff check {files}"}],
  "turn":  [{"name": "types", "run": "npx tsc --noEmit", "when": "**/*.{ts,tsx}"},
            {"name": "affected-tests", "run": "npx vitest related --run {files}", "when": "src/**"}],
  "verify": {"skill": "verify-kriminalist", "required_for": ["src/client/**", "src/app/**"]},
  "evidence_dir": ".conveyor/evidence",
  "budgets": {"fast_s": 10, "turn_s": 180},
  "gate": {"mode": "block"}
}
```

- `fast` — проверки по изменённым файлам, секунды.
- `turn` — глубже: типы, затронутые тесты (через `pytest_gate.py`/heavy-gate), только если совпал `when`.
- `verify` — какой verify-скилл доказывает пользовательские изменения и для каких путей он обязателен.
- `gate.mode`: `block` | `warn` | `off`. Менять его вправе только пользователь (см. C4: изменения профиля,
  ослабляющие гейт, требуют подтверждённого сообщения пользователя).
- **Автоопределение без профиля:** `package.json` scripts `lint`/`typecheck`, `eslint.config.*`, `tsconfig.json`,
  `pyproject.toml` с ruff/mypy. Ничего не найдено → только журнал приёмки (C4), без кодовых проверок.

### C2. Исполнитель проверок `~/.claude/scripts/conveyor/check.mjs`

Одна точка, которую зовут и `luna.sh`, и хуки Claude, и сам Claude вручную.

- Вход: корень репо, уровень (`fast` | `turn`), список изменённых файлов (по умолчанию `git diff --name-only`
  против базы задачи + неотслеживаемые).
- Выполняет команды профиля с подстановкой `{files}`, соблюдая бюджеты; тяжёлые команды — через heavy-gate.
- Выход: JSON-отчёт (команда, код возврата, первые N строк ошибок, длительность) в
  `~/.claude/conveyor/runs/<run>/report.json` и краткая сводка в stdout.
- Не правит файлы, не ставит зависимости. Отсутствующий инструмент — статус `skipped` с причиной, не падение.

### C3. Гейт исполнителя («крутиться у гейта до зелёного»)

Одна логика, три точки вызова: `luna.sh` (Codex: Sol, Luna), обёртка Gemini, хук `SubagentStop` (сабагенты
Claude: Sonnet, Haiku; хук блокирует завершение сабагента и возвращает ему вывод проверок). Для обёрток —
после завершения write-задачи и до выдачи результата:
1. Определить изменённые файлы в `-C` (снимок `git status` до запуска и после).
2. Запустить C2 `fast`, затем `turn`.
3. Если упало — продолжить тот же поток Codex (как уже делает model-error retry) с сообщением:
   какие проверки упали, вывод, «исправь причину, не ослабляй проверки и тесты». До 2 раундов.
4. В результат добавить раздел `## Gate` (что запускалось, итог по раундам); в `.status` — `gate=pass|fail|skipped`.
5. Если после раундов красное — `state=gate-failed`; Claude видит это в `luna-status.sh` и решает сам.

Отключение гейта на одну задачу — только по словам пользователя: Claude делает
`conveyor ledger waive gate --quote "<слова пользователя>"` (цитата проверяется по транскрипту, как в C4) и
передаёт `LUNA_GATE_SKIP=<id исключения>`; `luna.sh` пропускает гейт, только если такое исключение есть в
журнале сессии с проверенной цитатой. Каждое отключение пишется в статус, журнал и метрики.

### C4. Журнал приёмки и гейт «готово» (Stop-хук)

Против двух крупных классов ошибок: потерянные указания и раннее «готово».

- **Журнал** — файл на сессию и репо: `~/.claude/conveyor/ledgers/<session>.json`. Пункты: `id`, `text`
  (требование своими словами), `source` (цитата пользователя), `status`
  (`open` | `done` | `waived`), `evidence` (пути к артефактам, команды и их коды, ссылки на отчёты C2/verify).
- **CLI** `conveyor ledger add|evidence|done|show|waive` — Claude ведёт журнал этими командами.
- **Когда журнал обязателен:** в сессии были изменения кода (write-задача Luna с `-C` в git-репо или правки
  Claude в файлах кода). Чистые вопросы, исследование, правка документов — без журнала.
- **Stop-хук** (`~/.claude/hooks/conveyor-stop-gate.mjs`):
  - изменения кода есть, журнала нет → блок: «заведи журнал приёмки по требованиям пользователя»;
  - есть пункты `open` → блок со списком;
  - у `done`-пункта нет доказательства или доказательство старше последнего изменения кода → блок;
  - пользовательские пути из `verify.required_for` изменены, а доказательства verify нет → блок;
  - **страховка независимо от исполнителя:** прогоняет C2 `turn` по всем изменениям репо с начала задачи
    (кто бы их ни сделал); красное — блок с выводом;
  - анти-зацикливание: учитывает `stop_hook_active`; после 3 блоков подряд в одном ходе переходит в `warn` и
    пишет событие для метрик.
- **Исключение (`waived`) — только словами пользователя.** `conveyor ledger waive <id> --quote "<слова>"`;
  хук проверяет, что цитата — подстрока подлинного сообщения пользователя в транскрипте (повтор логики
  `verifyEventProvenance`). Агент не может выдать исключение сам.
- **Ослабление профиля** (`gate.mode` в `warn`/`off`, удаление проверок) хук распознаёт по диффу профиля и
  требует такую же подтверждённую цитату пользователя.

### C5. Верификация реальным запуском

- **Скилл `conveyor-setup`** (порт `create-verification-skill` из pstack, адаптированный под нас):
  опрашивает репо (поверхность, запуск, чем управлять, что наблюдать, изоляция), пишет `.claude/conveyor.json`,
  проектный скилл `.claude/skills/verify-<app>/SKILL.md` (Launch с пустых данных, Doctor, Drive, Evidence,
  Cleanup) и карту фич `.claude/skills/verify-<app>/features/*.md` (как добраться, как прогнать, какое
  наблюдаемое состояние доказывает работу, подводные камни). Перед сдачей прогоняет скилл один раз от начала до
  конца.
- **Скилл `conveyor-verify-maintain`** (порт `maintain-verification-skill`): сверяет карту фич с кодом,
  прогоняет вживую, обновляет; не может «починить» баг правкой документации.
- **Доказательства** — в `evidence_dir` (в `.gitignore`): скриншоты, логи, ответы API, видео, если доступно.
  Для интерфейса по умолчанию — Playwright или встроенный браузер, скриншоты desktop + mobile.
- **Оценка скриншотов моделью** (ступень 2 лестницы Orobator): при наличии verify-доказательств критик-
  «рядовой пользователь» получает скриншоты и проверяет видимость состояния: что выбрано, какая фаза, что
  делать дальше. Это прямой ответ на класс «непонятный интерфейс».
- **Новые проекты:** SessionStart в git-репо без профиля показывает одну строку «для этого проекта нет
  конвейера: запусти conveyor-setup» (не чаще раза в неделю на репо). До настройки работают умолчания C1.

### C6. Поправка → проверка (замыкание петли)

- Петля обучения уже ставит предложенные проверки в очередь (`checks.md`, сделано 2026-11-16).
- **Скилл `conveyor-correct`** (порт `/correct`): берёт открытые проверки очереди и классы ошибок проекта
  (повторились ≥ 2 раз), чинит каждую на самом высоком работающем уровне: архитектура → типы/линтер (сообщение
  об ошибке называет, что использовать вместо) → тесты → проза. Каждая новая проверка обязана упасть на
  реальной прошлой ошибке (доказательство в отчёте). Для существующих нарушений — «только новые добавления».
- **Таблица правил** в `AGENTS.md` проекта: правило ↔ чем обеспечено. Правило без обеспечения при повторе
  сразу поднимается на уровень выше. Правило удаляется, когда ошибка стала невозможной.
- **Исключения** в проверках — только на строке, с причиной, сроком и подтверждением пользователя.
- Запуск: по запросу пользователя или по предложению на старте сессии, когда в очереди есть проверки для
  текущего проекта. Никогда автоматически.

### C7. Критики с доказательствами

- Критики получают журнал приёмки и доказательства verify (а не только дифф): «Ревизор пробелов» сверяет

## 6. Поток одной задачи

1. Пользователь даёт задачу. Claude заводит журнал приёмки: пункты из его явных требований с цитатами.
2. Claude пишет бриф (как сейчас) и включает в него пункты журнала и команду verify, если нужна.
3. Исполнитель уровня из C0 (сложное: Sol 6.1 → Sonnet; простое: Gemini → Luna → Haiku) выполняет; гейт C3
   прогоняет `fast`/`turn`, при падении возвращает исполнителю (≤ 2 раунда).
4. Claude проверяет дифф, запускает verify-скилл для пользовательских изменений, складывает доказательства,
   отмечает пункты журнала.
5. Критики получают дифф + журнал + доказательства; находки с конкретикой; принятое — в раунд исправлений.
6. Claude пытается закончить ход — Stop-гейт C4 сверяет журнал и доказательства.
7. Повторяющиеся классы ошибок и поправки пользователя → очередь проверок → `conveyor-correct`.

## 7. Решения, принятые мной (проверьте)

- **Пилотный проект — kriminalist:** больше всего поправок про интерфейс, уже есть Playwright, есть живые
  сценарии. Затем rpg (нет прогона интерфейса — самый большой пробел), затем jewel.
- **Гейт C4 по умолчанию `block`**, но только для сессий с изменениями кода. Первые 7 дней после установки —
  `warn` во всех проектах, чтобы откалибровать ложные срабатывания по метрикам, затем `block`.
- **Раундов гейта C3 — 2.** Больше — признак, что задача плохо поставлена; решает Claude.
- **Критики не запускают тесты сами** (тестовый бюджет); воспроизведение high/critical — отдельным дешёвым
  шагом.
- **Журналы и отчёты хранятся в `~/.claude/conveyor/`**, доказательства — в репо проекта под `.gitignore`;
  уборка старше 14 дней — в существующий `luna-clean.mjs`.
- **Хуки Claude на Write/Edit (`fast`)** включаются тоже, но для кода, который пишет сам Claude, это редкий
  случай; основной путь — C3.

## 9. Риски

- **Ложные блоки Stop-гейта раздражают** → калибровочная неделя `warn`, анти-зацикливание, точные условия.
- **Гейт C3 удлиняет задачи** → бюджеты, только изменённые файлы, только затронутые тесты.
- **Verify хрупкий** (сиды, порты, состояние) → изоляция данных на прогон, Doctor-проверка, обслуживание
  карты фич отдельным скиллом.
- **Исполнитель «чинит» гейт ослаблением проверок** → правило в сообщении гейта + детектор правок
  конфигов линтера/тестов в диффе, с показом в `## Gate`.
- **Правка `luna.sh` ломает живые задачи** → `.next`, тестовый прогон копии, подмена в простое.

## 10. Оставлено строителю

состав автоопределения в C1; тексты сообщений гейтов (короткие, с конкретным следующим шагом).
